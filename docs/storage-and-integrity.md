# Storage and Event Integrity

The SQLite store provides typed project/authorization/mission/asset/evidence/finding/approval/worker-task persistence plus case, timeline, remediation, threat-intelligence, report, and worker-assignment records and a transactionally appended, per-project hash-linked event sequence. Domain-record revisions and their audit events are committed atomically. An append takes SQLite's write reservation before reading the current project head, computes the canonical event digest, and commits the event in the same transaction. This serializes concurrent writers within the database.

The event chain detects modification, reordering, and deletion within the retained sequence when verified against a trusted head. Current domain-record rows are also compared with their latest recorded record digests, so row tampering or deletion is detected against the retained event history. A local hash chain alone does not prevent an attacker with write access from rewriting the entire database or truncating the unanchored tail. Independent tamper evidence requires an external anchor and trusted head publication. Those L3/R-12 controls remain open and are not claimed as implemented.

Typed core records are validated against their JSON Schemas before persistence. SQLite schema evolution uses a forward-only transactional migration runner; the current schema version is 2. Case, remediation, threat-intelligence, report, and worker-assignment records use the generic versioned domain-record store. External anchoring and trusted-head publication remain separate L3/R-12 work and are not implemented.
